Scope them like service accounts: each tool gets only the permissions needed to do its job, and no more [prompt-injection-is-untrusted-input--least-privilege-for-tools].

Practically:

- **Give tools minimum useful scope.** A document-search tool should read, but not get write access “just in case” [prompt-injection-is-untrusted-input--least-privilege-for-tools].
- **Put destructive or outbound actions behind user-visible confirmation** so a silent injection cannot trigger them alone [prompt-injection-is-untrusted-input--least-privilege-for-tools].
- **Validate tool arguments as if a stranger typed them**, because in an injection case that is effectively what happened; path traversal, injection, and unvalidated input remain the failure modes [prompt-injection-is-untrusted-input--least-privilege-for-tools].
- **Keep high-trust tools far from untrusted retrieved content** in the flow. The worse your day gets when a single turn both reads attacker-controllable text and holds a loaded tool [prompt-injection-is-untrusted-input--least-privilege-for-tools].
- **Avoid the dangerous loop:** model reads external text, then calls a tool that exfiltrates data over the network while running unattended. Gate the tool or sanitize what reaches it to defuse most realistic attacks [prompt-injection-is-untrusted-input--least-privilege-for-tools].
