You set two different timeouts because an LLM API call can fail in two distinct ways that need different limits:

- **Connect timeout**: the provider is unreachable, so you want to give up quickly after a second or two [llm-api-from-php-in-production--two-timeouts].
- **Total/request timeout**: the provider is reachable but slow to finish generating, and you may be willing to wait longer because a real answer is still coming [llm-api-from-php-in-production--two-timeouts].

Using only one timeout would force those two very different situations into the same limit. With Guzzle, for example, `connect_timeout => 2` handles unreachable-provider failures quickly, while `timeout => 30` bounds how long you wait for a non-streaming answer to finish [llm-api-from-php-in-production--two-timeouts].

For streaming calls, the total timeout concept changes: instead of bounding the whole call, you may bound the idle gap between chunks because the connection stays open while tokens arrive [llm-api-from-php-in-production--two-timeouts]. That can also reduce retry pressure caused by users waiting on a blank screen and perceiving the request as frozen [llm-cost-at-campus-scale--streaming-and-retries].
