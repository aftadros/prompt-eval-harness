Scope them the way you’d scope a service account: least privilege, narrow permissions, and explicit boundaries [prompt-injection-is-untrusted-input--least-privilege-for-tools]. If the model can call tools, treat every exposed tool as part of its capability list, because it will eventually be coaxed into using all of them [prompt-injection-is-untrusted-input--least-privilege-for-tools].

Specifically:

- Give each tool only the minimum scope that makes it useful. A document-search tool should read; it shouldn’t get a write path “just in case” [prompt-injection-is-untrusted-input--least-privilege-for-tools].
- Keep destructive or outbound actions behind a confirmation the user actually sees, so a silent injection can’t trigger them alone [prompt-injection-is-untrusted-input--least-privilege-for-tools].
- Validate tool arguments as if a stranger typed them. In an injection case, that stranger effectively did; path traversal, injection, and unvalidated input remain real failure modes [prompt-injection-is-untrusted-input--least-privilege-for-tools].
- Keep high-trust tools and untrusted retrieved content as far apart in the flow as you can. The more a single turn both reads attacker-controllable text and holds a loaded tool, the worse your exposure becomes [prompt-injection-is-untrusted-input--least-privilege-for-tools].
- Break the dangerous loop: a model that reads untrusted external or retrieved text, then calls an unattended network or exfiltration tool. Gate the tool or sanitize what reaches it [prompt-injection-is-untrusted-input--least-privilege-for-tools].

In short, don’t give the model broad actions by default. The injection is only a foothold; the tools decide how much damage that foothold can cause [prompt-injection-is-untrusted-input--least-privilege-for-tools].
