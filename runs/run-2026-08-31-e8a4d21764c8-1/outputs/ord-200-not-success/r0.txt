A 200 status code only means the HTTP layer succeeded; it says nothing about whether the body is actually usable. As the document puts it, "a model can return a clean 200 with a body that's malformed, off-topic, or hostile, and the HTTP layer will file that under success" [llm-api-from-php-in-production--a-200-is-not-success]. In other words, the response is untrusted input from the moment it arrives.

The document recommends treating it accordingly: if you asked for JSON, parse and validate against a schema before anything downstream touches it, and treat a parse failure as a retryable error rather than a crash; if the text will be rendered, escape it like any user-supplied string (since a model that read an attacker's document can echo an attacker's script). Output validation belongs on the reliability surface next to timeouts, not off in a security backlog [llm-api-from-php-in-production--a-200-is-not-success].
