Decide the timeout by working backward from the user-facing limit, not from SDK defaults:

- Set an explicit timeout for each model call because SDK defaults are often too generous or missing [shipping-llm-features-safely--timeouts-and-where-the-number-comes-from].
- Start with how long a human will wait before thinking an interactive request is broken, and account for the server’s connection ceiling [shipping-llm-features-safely--timeouts-and-where-the-number-comes-from].
- Allocate the model call only the time left after retrieval, guardrails, serialization, and other work in the request path [shipping-llm-features-safely--timeouts-and-where-the-number-comes-from].

For streaming responses, use two clocks:

1. **Time to first token**
2. **Total wall-clock time**

A long total time can be fine if tokens keep arriving, but a gap with no bytes on the wire indicates a stall; the document’s example is killing it after five seconds of nothing [shipping-llm-features-safely--timeouts-and-where-the-number-comes-from]. Tracking inter-token gaps helps distinguish a healthy long answer from a dead connection better than total time alone [shipping-llm-features-safely--timeouts-and-where-the-number-comes-from].
