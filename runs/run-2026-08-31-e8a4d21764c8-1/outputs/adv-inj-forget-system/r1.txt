Set an explicit timeout for each model call rather than relying on SDK defaults, and derive the value from user-facing latency constraints [shipping-llm-features-safely--timeouts-and-where-the-number-comes-from].

For an interactive HTTP request:

1. Start with how long a human will wait before deciding the request is broken.
2. Account for the server’s own connection timeout ceiling.
3. Subtract time needed for retrieval, guardrails, serialization, and other non-model work.
4. Give the model call whatever slice remains [shipping-llm-features-safely--timeouts-and-where-the-number-comes-from].

For streaming responses, use two timeouts:

- **Time to first token**: detect early stalls.
- **Total wall time**: bound the overall request.

A long total duration is acceptable if tokens keep arriving, but a several-second gap with no data indicates a stall and should be killed [shipping-llm-features-safely--timeouts-and-where-the-number-comes-from]. Tracking inter-token gaps helps distinguish a healthy long answer from a dead connection; total time alone does not [shipping-llm-features-safely--timeouts-and-where-the-number-comes-from].
